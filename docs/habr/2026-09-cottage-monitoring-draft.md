# Как мы вынесли умный дом в облако и не отдали мозг Home Assistant

У нас усадьба на профессиональной автоматизации: LogicMachine, KNX, Zigbee, Modbus, тёплые полы со своим Lua-алгоритмом. Дом работает локально. Если пропадёт интернет, свет, отопление и сценарии остаются на контроллере.

Но хочется истории, графиков, «выключи свет на втором» из Telegram и нормального экрана для семьи. Типовой путь в таких историях — поставить Home Assistant и пустить его на шину. Мы пошли иначе.

**Контроллер остаётся мозгом. Облако снимает телеметрию, хранит историю и отдаёт управление через один каталог операций. Home Assistant — витрина поверх этого каталога, а не новый мозг дома.**

Статья — отчёт о полугоде разработки: сервер, клиент на LogicMachine, нагрузка на контроллер, обрывы связи, агент (Hermes / OpenClaw) и подключение Home Assistant. С инцидентами, которые не видно в README.

## Что за дом и зачем облако

На шине порядка **200 объектов**. Двадцать линий света с отдельным feedback, четырнадцать зон тёплого пола, Zigbee-датчики воздуха, счётчик, погода, чайник по BLE. LogicMachine сводит протоколы к объектам KNX: записал значение в групповой адрес — дернулось железо.

Локальный UI контроллера (Mosaic) для семьи неудобен. Grafana хороша оператору, но это не «включить свет в ванной». Голосовые и чат-агенты не понимают `1/1/15`. Home Assistant умеет красиво рисовать комнаты, но если отдать ему KNX и MQTT напрямую, автоматизации разъедутся: часть на контроллере, часть в HA, часть в боте.

Поэтому облачный контур с самого начала проектировался как **надстройка**, а не замена:

- сценарии и алгоритм полов живут на LogicMachine;
- в облако уходит телеметрия;
- обратно — команды «адрес + значение» с подтверждением;
- все внешние клиенты (агент, HA, кто угодно дальше) ходят в один сервис.

Сервис мы назвали **Nord** — северный вход. Один процесс FastAPI: MQTT-ingest, REST, MCP.

```
Устройства (KNX / Zigbee / Modbus / BLE)
        │
        ▼
 LogicMachine (Lua daemon + локальные сценарии)
        │  MQTT TLS :8883
        ▼
    Mosquitto  ──►  Nord (FastAPI)
                       │
          ┌────────────┼────────────┐
          ▼            ▼            ▼
     TimescaleDB     Redis      Grafana (SELECT)
          ▲
          │
   Telegram / OpenClaw / Hermes     Home Assistant
        (MCP)                            (REST Ops)
```

Связь дома с облаком — только MQTT. Облако не ходит на контроллер по HTTP в штатном режиме. Это важно: контроллер сидит в LAN, у него старый OpenSSL, FTP вместо SCP и лимиты Lua, о которых ниже.

Разработка шла волнами, почти как в спеках: март — сервер, сразу следом клиент, лето — агент и «боевое» железо, август — единый каталог операций и HA.

## Волна 1. Сервер: ingest, история, команды

Первый месяц — не UI. Нужен был приём телеметрии и путь команды обратно.

Стек скучный и нарочно такой: Python 3.12, FastAPI, aiomqtt, PostgreSQL + TimescaleDB, Redis для актуального среза, Mosquitto, nginx, Grafana. Контейнер собирается локально, на сервер уезжает образ, не `git clone` и не rsync исходников. На VPS — `docker load` / `docker pull`, миграции, systemd. Сам Nord слушает loopback `:8321` в bridge с `host-gateway`; Home Assistant позже пришлось оставить на host-network, иначе контейнер HA не достучался бы до `127.0.0.1:8321`.

Протокол MQTT v1 живёт в namespace:

```text
cm/<house_id>/<device_id>/v1/
```

В проде префикс пустой, в dev — `dev/`, чтобы тестовый клиент не писал в живой дом. Контроллер публикует события, retained-состояние по групповым адресам, схему объектов (`meta/objects`, при >100 объектов — чанками) и LWT `status/online` / `status/offline`. Сервер публикует команды в `…/cmd`, ждёт ack в `…/cmd/ack/{request_id}`.

Идемпотентность событий мы сознательно **не** делали: QoS 1 может принести дубль, и это отдельная строка в журнале. Дедупликация «по GA, оставить последнее» ломает историю on→off→on. Для среза есть `current_state` и Redis, для графиков — гипертаблица `events`.

Команда — не fire-and-forget. В БД пишется `commands` со статусом, сервер матчит ack по `request_id`, считает RTT. На живом тесте «включить холл → подождать → выключить» вышло примерно **2.5 с на ON и 0.5 с на OFF** до ack. Это уже не HTTP к контроллеру, это шина плюс Lua.

## Волна 2. Клиент на LogicMachine

LogicMachine — не Linux-сервер, на который можно накатить systemd-юнит и забыть. Приложение — LM App: форма настроек, daemon на Lua 5.1, библиотеки `mosquitto`, `localbus`, `grp`, `json`, `encdec`.

Почему не event-скрипт на каждый групповой адрес? Объектов 200, скриптов станет 200, отладка умрёт. Почему не polling `grp.getvalue`? Задержка и лишняя нагрузка. Слушаем шину через `localbus`: `groupwrite` → буфер → MQTT.

Цикл демона в первом приближении такой:

```lua
while true do
  lb:step()            -- KNX
  client:loop(timeout) -- MQTT, всегда, даже offline
  process_buffer()
  os.sleep(loop_sleep)
end
```

Мелочь, которая стоила reconnect-storm: обёртка mosquitto на LM иногда возвращает `true` из `loop()`. Код считал ошибкой всё, что `~= 0`. В Lua `true ~= 0`, поэтому «успешный» loop выглядел как ошибка, демон рвал TCP и начинал заново. Handshake TLS при этом не успевал завершиться: сокет на :8883 есть, `ON_CONNECT` нет. Починили так: ошибка только если `type(rc) == 'number' and rc ~= 0`, а `loop()` крутится на каждой итерации.

Ещё одна платформенная радость: **слишком большой daemon не стартует**. Полный вариант (~25 КБ, десятки top-level `local`) на этой LM молча не поднимается. Рабочий размер — порядка **10 КБ**, состояние в таблицах `C`/`S`, а не россыпью локалей. Деплой не в ту папку (`data/…/daemon/` вместо `/daemon/cottage-monitoring/daemon.lua`) даёт ещё красивее: Apps «запущен», крутится старый код. SCP контроллер не умеет, только FTP через `lftp`. Надёжный цикл: `stop` → залить файл → `start`, не надеяться на `restart`. Перед заливкой watchdog лучше поставить на паузу, иначе он бьёт процесс прямо во время обновления.

Отдельно: после пропадания питания штатный супервизор LM **не** поднимает App daemon сам. Нужен Config → Save (или наш HTTP start). Это всплыло ещё в апреле, задолго до TLS.

При обрыве MQTT события не теряем сразу: RAM-буфер FIFO, по умолчанию 1000 записей, без дедупликации, при переполнении выкидываем старые. На `ON_CONNECT` — flush. Storage на флеш для буфера отвергли: spec требует RAM, на LM это ещё и медленнее.

## Нагрузка на контроллер: как мы сами себя укусили

Первая оптимизация протокола была правильной. Публиковать каждое `groupwrite` дважды (event + retained state) при активной шине — дорого. Ввели пакеты:

- `events/batch` — пачка событий одним publish;
- `state/batch` — пачка состояний;
- плюс по-прежнему retained `state/ga/<ga>` для тех, кто хочет точечный срез.

Интервал батча по умолчанию **1.5 с**, максимум **50** событий. На сервере это отдельные хендлеры, не «распаковать в N одиночных». Сверху три рычага CPU:

- `throttle=20` — лишние groupwrite в ту же секунду **молча отбрасываются** (очереди нет);
- `event_sleep=0.03` после каждого события;
- `loop_sleep=0.25` у главного цикла (~4 Гц вместо 6–7).

Бенч на самой LM показал ожидаемое: грузит **число publish**, не размер payload. «Крутить только sleeps без батча» на активной шине почти не помогает.

Потом случился compact rewrite демона. Нужно было уложиться в лимит локалей и размер. В компактной версии **перестали читать `batch_interval`**: каждое KNX-событие снова давало два MQTT publish, а heartbeat писал storage три раза за цикл, roughly 6–7 Гц.

График loadavg контроллера не врёт. До compact — около **0.85**. С полуночи после выкладки — около **1.58**, почти ×1.8. DRM88 и опрос Modbus не меняли, виноват был только демон телеметрии.

Метрику мы не снимаем node_exporter’ом: на контроллере его нет. Resident `load-to-grp.lua` читает `/proc/loadavg` и пишет в KNX `34/1/6` (1 мин), `34/1/7` (5), `34/1/8` (15). Дальше обычный путь: шина → MQTT → Timescale → Grafana `cottage-lm-load`, алерт load15 > 2.0 в Telegram. Контроллер уже в шине, отдельный агент мониторинга не нужен.

Вернули батчинг (v1.1.2), heartbeat в storage раз в 3 секунды, мягче sleeps. Цифры «вернулось к 0.85» в репозитории нет — для статьи лучше вставить сам график из Grafana. Урок простой: на встраиваемом контроллере «сделать код короче» ≠ «сделать его дешевле». Нужен метрик с шины, иначе оптимизация под лимит Lua съедает CPU.

Отдельный бюджет CPU — resident Modbus, который сводит железо к виртуальной KNX. Температуры контуров (Razumdom) пишут в `1/3/*` только при |ΔT| ≥ 0.5 °C. Реле DRM88ER опрашиваются каждые **0.5 с**, но на шину уходит только смена 0↔1. Батчинг MQTT лечит сторону облака; плотный poller рядом — другая статья расходов. В инциденте 17 июля мы их сознательно не трогали: сначала вернуть то, что сами сломали.

## Обрывы связи: LWT врёт не всегда так, как кажется

Штатная модель обрыва:

1. брокер не видит keepalive → LWT `status/offline`;
2. демон кладёт события в RAM-буфер;
3. reconnect → `status/online` → flush;
4. сервер обновляет `last_seen`.

На бумаге красиво. В проде всплыли три разных класса отказа, и watchdog, который смотрит только на «процесс жив + MQTT online», ловит не все.

### Класс 1. Процесс жив, телеметрии нет

2 августа события в проде остановились около 13:07. До этого шло **80–110 events/мин**. Сервер был здоров, `/health` 200, ingest онлайн. На контроллере процесс демона жив, PID тот же с июля, uptime две недели. В MQTT раз в минуту приходит `status/health` с `mqtt_connected: true`. А `events/batch` — тишина.

Первый разбор по retained health принял «живой поток» за живой. Retained сообщение с ts=13:07 выглядело как пульс. На деле брокер уже писал: клиент превысил keepalive, disconnect, LWT.

Дальше оказалось интереснее, чем «зомби localbus».

### Класс 2. TLS, который ломается не в день ротации

LogicMachine — старый OpenSSL. Let's Encrypt `fullchain` с intermediate **YR2** (3 PEM) на нём не хендшейкится. Короткая цепочка **R12** (2 PEM) работала. Certbot с июля всё равно начал отдавать YR2, даже с `preferred_chain = ISRG Root X1`.

Мы научили deploy-hook: если live — 2 PEM, копируем; если больше — пытаемся взять ещё живой R12 из archive; иначе **обрезаем** newest fullchain до leaf + один intermediate. Mosquitto держит копию файлов, не symlink на live.

29 июля цепочка на брокере стала trimmed YR2. Клиент с включённым `mqtt_tls_verify=true` и CA-файлом ISRG Root X1 эту цепочку **не валидирует**. Но уже установленный TLS-сеанс, поднятый ещё на R12, жил без re-handshake. Дома всё работало четыре дня. 2 августа keepalive оборвался — и каждый новый handshake падал: `tlsv1 alert unknown ca`. Watchdog честно долбил hard restart каждые пять минут. Рестарт процесса не лечит несовпадение сертификата.

Фикс: вернуть verify off (это и был default для LM) + restart. Соединение с первой попытки. Правило, которое теперь в runbook: `mqtt_tls_verify` включать только с CA, который покрывает **текущую** цепочку брокера; после каждого renew — проверять handshake именно с контроллера, не `openssl s_client` с ноутбука.

### Класс 3. Watchdog смотрит не туда

Штатный супервизор LM перезапускает daemon **только если процесс упал**. Resident watchdog ловит как раз случай «жив, но сломан». Эскалация раз в минуту: сначала soft-флаг в storage (демон сам делает `error()` и его поднимает LM), если за 45 секунд не помогло — HTTP hard restart через Apps API, cooldown 5 минут.

Он сторожит heartbeat (120 с) и флаг MQTT (10 мин offline). Если демон в «зомби» — цикл крутится, health публикуется, localbus/батч молчит — watchdog считает систему здоровой. Поле `status/health` сервер **вообще не парсит** (`unknown_topic`): `last_seen` дома кормится событиями и `status/online`, не health. Retained health с устаревшим ts легко принять за пульс.

Мы добавили `cm_last_event_ts` и условие **`events_stale`**: MQTT online, а событий нет дольше порога (по умолчанию 15 минут). С облака это дублирует алерт по `houses.last_seen` > 15 мин. Watchdog на контроллере этот алерт не заменяет.

И отдельно: hard restart с LM требует пароль админки в config. Без него watchdog умеет только soft-флаг. Есть и серверный путь: `POST /houses/{id}/restart-daemon` → команда `{"action":"restart"}` в MQTT → ack и самоперезапуск демона через пару секунд. Потому что заходить в Web UI контроллера каждый раз, когда «пропала телеметрия», — не операция, а ритуал.

Ещё одна ловушка операционки: init на LM **не** поднимает убитый resident. Обновил код watchdog в БД, убил процесс — новый сам не появится. Нужен свой скрипт: залить Lua, `db:update`, снять stale pidfile, руками spawn `scripting-resident.lua`. Это не баг нашего демона, это устройство платформы. Его надо знать до первого инцидента в 23:50.

## Lua и `false`: как выключить свет и получить `null` в облаке

Бот включил свет в холле второго этажа. Потом команда «выключить второй этаж». На сервере — timeout. В `current_state` для выключенного света — `null`. Физически лампы могли погаснуть: `grp.write` на контроллере отработал.

Две независимые ошибки в компактном демоне.

**Ack уходил не туда.** Сервер ждёт `cmd/ack/{request_id}`. Демон публиковал в голый `cmd/ack`. Шина меняется, запись в `commands` висит в timeout, ретраи и мониторинг врут.

**Идиома `ok and v or nil`.** После `pcall(grp.getvalue, …)` это выглядит безобидно. В Lua при `v == false` выражение даёт `nil`. Выключенный свет — это bool `false`. В MQTT улетало событие без `value` или с `null`, БД портилась, агент дальше принимал решения по мусору.

Починили явно:

```lua
local function safe_getvalue(addr)
  local okv, v = pcall(grp.getvalue, addr)
  if okv then
    return v  -- в том числе false
  end
end
```

Проверка после фикса: `grp.write(..., false)` → в MQTT `"value": false`, команда через API → `ok`, не `timeout`. Это тот класс багов, который unit-тест на ПК не поймает, если не прогнать именно `false`, а не `0`.

## Агент: MCP, Hermes, OpenClaw и русские падежи

К июлю телеметрия и команды по GA уже работали. Агенты (Hermes, OpenClaw, Cursor) этим пользоваться не могли: REST без нормальной модели «свет / климат / чайник», без ключей, с адресами вместо смысла.

Сделали MCP **в том же процессе**, что ingest. Не sidecar. Streamable HTTP на loopback, снаружи `/mcp` не торчит. Ключ `cm_…`, scopes `read`/`write`, грант на дом. Инструменты семантические: `set_lights`, `get_temperature`, `set_climate`, `set_kettle`, не «запиши 1/1/15».

Резолвер объектов сидит в Nord. Теги + имена с шины, лемматизация русских падежей через **pymorphy3**. «Выключи свет в гостиной» и «в гостиную» должны попадать в один GA. Ambiguous — ошибка, а не «возьми первый». Для записи, которая не должна касаться шины (бенч моделей), заголовок `X-Cottage-Dry-Run`: полный путь resolve + tool, в MQTT ничего не уходит, в `commands` статус `dry_run`.

Hermes подключается ровно как MCP-клиент:

```yaml
mcp_servers:
  cottage:
    url: http://127.0.0.1:8321/mcp
    headers:
      Authorization: "Bearer ${COTTAGE_API_KEY}"
```

С `/model` у Hermes всё честно, но нет изоляции «дом-агент с маленьким контекстом» рядом с большим общим чатом. Для бытовых команд это критично.

Замерили. Узкое место — не MQTT (~1 с на tool) и не шина. OpenClaw `main` на тяжёлой модели тащил в контекст десятки и сотни тысяч токенов cache, wall на «выключи свет» ощущался как минута. На одинаковом коротком промпте:

| Модель | средний wall e2e |
|--------|-----------------:|
| gemini-3.5-flash | ~5.6 с |
| мини-модели соседнего класса | ~6–8 с |
| тяжёлый sol / sonnet | ~11 с |

Отдельный агент `cottage` на Flash, без памяти «основного» ассистента, даёт уже не «×2», а часто заметно больше: контекст не раздут, reasoning для «свет / уставка / чайник» не нужен. Live в Telegram: свет по этажам, чайник, энергия по фазам.

По дороге выкинули `exec` + `mcporter` из рук агента. Модель периодически вызывала несуществующее `mcporter list-commands` и приносила в чат баннер `Exec failed`, даже когда skill это запрещал. Потом `TOOLS.md` в workspace снова учил CLI, хотя `AGENTS.md` запрещал `exec` — модель читает оба файла. Сейчас OpenClaw видит native MCP (`cottage__set_lights` и дальше), `exec` у дом-агента нет. mcporter остался для бенчей и отладки в шелле.

SDK MCP держим на 1.x. Двойка убрала `fastmcp` так, что одна сборка образа просто не стартовала. Клиент OpenClaw на хосте ещё 2025-era. Обновлять «потому что вышла спека» раньше клиента — лишний простой дома.

## Control и status: агент выключил этаж, лампы горели

KNX-свет устроен как в учебнике, и это ловушка для семантического слоя. Пишем в control `1/1/*`. Реальное состояние после выключателя на стене живёт в status `1/2/*`. Control часто так и остаётся `false`, хотя лампа горит.

Агент получил «выключи свет на втором этаже», вызвал `set_lights`. Ответ: выключен холл, остальное «уже выключено». Физически горели детские, кабинет, ванна. `skip_unchanged` смотрел на control. Плюс часть status-объектов без тега этажа — резолв «2 этаж» находил только те, у кого этаж в имени.

Фикс: on/off для skip и для отображения берём из status, пишем по-прежнему в control. Ту же дыру закрыли у чайника: `on` из state, не из cmd. Иначе агент говорит «уже включён», а чайник выключен.

Это не баг MQTT. Это цена семантического API над шиной, где feedback — отдельный объект. Если строите «умный» слой над KNX, закладывайте пары control/status в резолвер в первый же день, не после первого ночного «почему горит».

## Nord Ops: один каталог на бота и на HA

К августу MCP умел то, чего не умел REST, и наоборот. Новый чайник появлялся как tool и не появлялся как HTTP-операция. Список домов отдавал все дома, не гранты ключа. Команда в БД не помнила, кто её послал: Telegram или будущий HA.

Сделали реестр **Ops**. Имя операции = имя MCP-tool = сегмент URL. Диспетчер один: scope → дом из грантов → rate-limit на запись → handler. `GET /ops` и список MCP tools должны совпадать, это проверяется тестом. Колонка `commands.actor_key_id` пишется в единственной точке `send_command`, её нельзя подделать комментарием в payload.

Семнадцать операций на обе грани: свет, климат, автополы, датчики, энергия, чайник с уставкой, статус дома. Placement (`area` / `floor`) кладём в ответы read-Ops в Nord, чтобы HA не парсил русские имена сам. Синонимы резолвера («зал» → гостиная, «Настя» → Настина комната) тоже живут в облаке.

Telegram остаётся на MCP. HA ходит в REST `POST /api/v1/houses/{id}/ops/{name}`. Grafana по-прежнему не клиент Nord, а SELECT по Timescale. Три лица, один контракт, шина одна.

## Home Assistant: витрина, которой нельзя увидеть KNX

Семье нужен GUI по этажам и комнатам. Grafana — для нас. Mosaic — в LAN. Значит HA, но с жёстким non-goal: **не мозг дома**.

Что сделали:

- официальный Container, не HA OS и не Supervisor;
- слушает loopback, снаружи nginx + TLS + WebSocket;
- custom component опрашивает Nord Ops раз в 30 с (статус дома, свет, климат, температуры, влажность, батареи Zigbee, энергия, чайник);
- команды — те же Ops, что у бота;
- в HA нет интеграций KNX и MQTT, нет подписки на `cm/#`, `automations.yaml` пустой;
- люди логинятся учётками HA; в Nord все клики семьи — один сервисный ключ `home-assistant`.

Первый живой конфуз: после клика компонент сразу делал пачку read-Ops. Status на шине отстаёт на 0.5–3 с, poll видит старый off, UI откатывается, повторный клик на Zigbee/BLE пишет True ещё раз и выключает. Лечится оптимистичным стейтом и отложенным refresh на **2.5 с**, не «поллить чаще».

Второй: YAML-платформы HA читают snapshot **один раз** на setup. Клиент сначала не считал 404 ошибкой (чайнику без объекта уставки Nord отвечает 404). Если первый poll падал, `coordinator.data` был `None`, и `async_add_entities` разваливался. Фикс: любой HTTP ≥400 — ошибка; нет первого снимка — интеграция жива, сущности появятся после reload, когда Nord ответит.

Энергомониторинг HA читает часовую статистику recorder, не live. Сенсор завёлся вечером — август в Energy пустой. Импортировали 661 час из Timescale по счётчику: baseline, `sum = reading - baseline`, отдельно seed `statistics_short_term`, иначе recorder ставит нулевую точку на текущие десятки тысяч кВт·ч и график падает. Вышло около 500 кВт·ч за август — уже семейная цифра, не операторская.

Ещё мелочи с хоста, чтобы не повторять. go2rtc из `default_config` биндит WebRTC на `:18555` и на host-network это публичный порт — entrypoint переписывает на localhost. У погодных сенсоров recorder первые часы записал ветер и влажность в `unit_class=temperature`: графики чинятся правкой meta, не «пересоздай entity». Grafana iframe с `ha.` на соседний хост часто пустой из-за cookie — семье проще markdown-ссылка, чем анонимный Grafana.

Итог, который важен архитектурно: если завтра появится Алиса или свой веб, они встанут третьей гранью тех же Ops. Не третьим MQTT-клиентом на шину и не вторым набором автоматизаций.

## Что из этого, как нам кажется, новое

Не «придумали MQTT» и не «придумали HA». Новая здесь сборка ограничений встраиваемого контроллера и облачного семантического слоя:

1. **Пакетный MQTT именно ради CPU контроллера**, не ради брокера. Когда выкинули батч «чтобы демон влез в лимит Lua» — loadavg это показал за ночь.
2. **Схема с `schema_hash` и чанками meta**, чтобы 200 объектов переживали лимит размера сообщения и сервер видел смену состава дома.
3. **Offline-буфер FIFO без дедупликации** — история мигания важнее «последнего значения».
4. **Watchdog двухступенчатый и по потоку событий, не по PID.** Soft-флаг → HTTP hard; процесс жив и health retained — недостаточное условие.
5. **Loadavg через групповой адрес**, не через отдельный exporter: контроллер уже умеет писать в шину.
6. **Short-chain TLS под старый OpenSSL LM** и правило «проверять handshake с железа после renew».
7. **Семантический MCP с лемматизацией русских имён** над живыми тегами KNX, плюс dry-run для бенча агентов без удара по шине.
8. **Nord Ops: один каталог, две грани, актор команды в БД.** HA не получает отдельного API «для UI».
9. **HA как REST-клиент облака**, без KNX, без MQTT discovery, без домашних automation.
10. **skip и отображение света по status, запись в control** — иначе семантический слой врёт на любом доме с выключателями на стене.

## Что бы мы сказали себе в марте

**Сначала пары control/status и «кто мозг», потом интеграции.** HA и агент легко сделать вторым мозгом. Потом вы это расхлёбываете годами.

**Компактность Lua — ресурс, батчинг — тоже ресурс.** Их нельзя менять одно на другое без графика loadavg.

**Health — это не телеметрия.** Retained online, uptime две недели и «mqtt_connected: true» отлично уживаются с нулём событий.

**`false` в Lua — отдельный тест.** Любая обёртка вида `ok and value or nil` на bool-шине токсична.

**Агенту не давать shell «на всякий случай».** Он его вызовет. MCP tools и короткий skill лучше, чем CLI вокруг них.

**Сертификат, который сменился сегодня, может убить клиент через четыре дня**, на первом обрыве keepalive. Ротация TLS и клиент с pin CA — это один инцидент, растянутый во времени.

Дом при этом продолжает работать без облака. Это была цель номер ноль, и её мы не отдали ни агенту, ни Home Assistant.

## Что дальше

Живой контур уже в проде: телеметрия, Grafana, Telegram-агент, семейный HA. Из незакрытого операционного — слайдер уставки чайника (нужен отдельный объект на LM, число в bool-cmd ломает BLE), аккаунты семьи в HA People, спокойный апгрейд MCP SDK, когда подтянется клиент.

Если делаете похожее на LogicMachine или другом встраиваемом контроллере: не начинайте с витрины. Начните с честного протокола, батча, ack и проверки, что `false` доезжает до базы. Витрину прикрутите последней — и пусть она ходит в тот же каталог, что и бот.
